# משימה: להעלות את Habodek כמה רמות, לרמת code review של Claude Code

## רקע

Habodek הוא בוט ה-code review שלנו ל-merge requests ב-GitLab. הוא רץ ברקע:
webhook ← תור ← worker ← clone ← review ← threads על שורות ב-diff. אחר כך הוא עונה
למפתחים ובודק תיקונים.

**אתה לא מחויב לשום החלטה קודמת.** לא ל-fork, לא לשפה, לא לארכיטקטורה ולא למדדים
שנקבעו בעבר. המטרה היא מה שמתואר במסמך הזה.

כן כדאי להבין איך הגענו לנקודה הזאת. `ROADMAP.md` (מסמך ההעברה בין sessions) מתעד את
ההחלטות ואת הסיבות להן. תקרא אותו, וגם את `git log`, `agent/NOTICE.md`, `DEPLOY.md`
ו-`README.md`. תתייחס אליהם כרקע ולא כאילוצים.

## הבעיה

הבודק לא מספיק טוב, ואת זה לא פותרים בכיוונון prompt:

- **ה-agent חלש.** ה-code exploration לא מרגיש אמיתי. הוא לא בודק מי קורא לפונקציה
  ששונתה, מה החוזה שלה בצד השני ומה נשבר בעקבותיה.
- **הכול מרגיש כאילו דחפו prompt למודל AI בסיסי** והוא החזיר תשובה בלי להבין את
  ההקשר שמאחוריה.
- **באגים אמיתיים מתחבאים לפעמים בין 3 ספריות שונות.** השינוי נמצא באחת, החוזה בשנייה,
  והצרכן שנשבר בשלישית. במבנה הנוכחי הבודק לא יכול למצוא דבר כזה.
- **אין תהליך reasoning.** הוא לא מנסח השערה ובודק אותה, לא עוקב אחרי ראיה, ולא משנה
  דעה כשמשהו לא מסתדר. Claude Code כן עושה את כל זה כשמבקשים ממנו review.

## הרף

המטרה היא שהחשיבה של הבודק תהיה שקולה לפתיחת Claude Code על ה-repo עם הבקשה "תעשה CR
ל-MR הזה ותפרסם הערות".

אחר כך המפתח דוחף תיקון או מגיב ("תוקן", "זה מטופל ב-X", "זה by design"). בשלב הזה
הבודק צריך לבדוק את התיקון או את הטענה כמו ש-Claude Code היה בודק: ללכת לקוד, לאמת,
ולשנות דעה רק כשיש ראיה.

כל זה צריך לקרות בשירות שרץ ברקע, בלי אדם ליד המקלדת.

**המטרה היא מוצר ברמה גבוהה.** לא ציון במדד ולא שיפור הדרגתי.

## אילוצים

- **מודל:** מה-LiteLLM של החברה. יש שתי אפשרויות: `qwen3.8 flash next` או
  `GLM5.3 flash`. שניהם חזקים משמעותית ממה שהבודק נבנה עבורו, ואפשר להשתמש במלוא
  ה-context window שלהם.
- **עלות:** אין מגבלה על טוקנים. אל תחסוך בקריאות, בהקשר או ב-reasoning על חשבון
  האיכות. גם latency פחות קריטי כי זה רץ ברקע, אבל תגיד כמה זמן ייקח review של MR טיפוסי.
- **סביבה:** השירות רץ על מכונה ב-VPN בלי גישה לאינטרנט.
- **כלים חיצוניים:** כל כלי, ספרייה או agent חיצוני חייב להיות open source, ואפשר יהיה
  להעביר אותו ל-VPN ולהריץ אותו שם offline. זה כולל את כל התלויות שלו, ואסור שתהיה לו
  קריאה החוצה בזמן ריצה. שירות מנוהל או כלי closed-source לא באים בחשבון.

## מה כבר ראיתי בקוד (נקודת פתיחה בלבד, תאמת בעצמך)

- **ה-review שרץ בפועל הוא שתי קריאות LLM בודדות בלי לולאת tools.** הנתיב הוא
  `runStructuredChunkReview` ב-`agent/internal/core/review/structured_review.go`.
  - שלב ה-extraction רואה רק את ה-diff ואת הקבצים שהשתנו: קובץ מלא עד 400 שורות, ומעל
    זה קטעים של ±12 שורות.
  - ה-prompt שלו אומר במפורש `Only analyze changed code shown in the bundle` ו-`Prefer
    false negatives`.
  - שלב ה-verification מקבל ראיות שנאספות פעם אחת, לפי בקשה אחת של המודל (paths,
    symbols, patterns). הוא לא יכול לעקוב אחרי ממצא ולשאול שאלת המשך.
- **יש לולאת agent אמיתית עם 9 tools, אבל לפי מה שראיתי אף אחד לא מפעיל אותה.** היא
  נמצאת ב-`agent/internal/core/agents/reviewer/agent.go` ומחוברת ב-DI, אבל
  `pipeline.go` אף פעם לא קורא ל-`p.agent`. גם היא מוגבלת: `agentMaxTokens = 4096`
  ודחיסת context גסה ששומרת רק את ההודעה הראשונה ואת שלוש האחרונות.
- **גם החצי השני הוא קריאת LLM אחת בלי tools.** זה נכון לתשובה למפתח
  (`agent/internal/core/agents/replier`) ולבדיקה החוזרת אחרי push
  (`agent/internal/core/review/verdict.go`). ה-reply מקבל ±20 שורות סביב העוגן, ה-verdict
  מקבל ±30, ולשניהם יש תקרה של `replyMaxTokens = 600`. כשמפתח כותב "זה מטופל ב-middleware",
  אין לבודק דרך ללכת ולבדוק.
- **הרבה מהמגבלות האלה נבנו למודל קטן עם context קצר.** קטעים במקום קבצים, תקרות טוקנים
  נמוכות, דחיסה אגרסיבית ו"עדיף לפספס". עם המודלים החדשים ועם context מלא, רוב ההנחות
  האלה כבר לא נכונות.

## על מה אני רוצה שתחשוב

אני לא מחפש תיקון prompt. תחשוב ברצינות מה ההבדל בין review של Claude Code ל-review
של Habodek, ואיך סוגרים את הפער. אלה השאלות שאני רוצה תשובה עליהן:

1. **המודל.** איך מנצלים את qwen3.8 flash next או את GLM5.3 flash עד הסוף: thinking
   mode, תקציבי reasoning ומלוא ה-context. תנסה את שניהם על משימות review אמיתיות
   ותמליץ על אחד, או על שילוב שלהם (למשל אחד שחוקר ואחד שמאמת).
   - תבדוק איך הם מחזיקים סשן agentic ארוך עם הרבה tool calls דרך LiteLLM. אלה גרסאות
     flash, וה-harness צריך להתאים את עצמו למה שהן טובות וחלשות בו.
   - אם אין לך גישה ל-gateway, תשאל אותי ואל תנחש.
2. **המנוע: לבנות או לשלב.** השאלה היא מה ה"מוח":
   - לולאת agent משלנו, או
   - agent בקוד פתוח שרץ headless בתוך checkout מבודד, ושכבה דקה סביבו מנהלת את
     GitLab, התור וה-threads.

   תבחר לפי מה שייתן את המוצר הכי טוב, ולא לפי מה שכבר קיים. שמור קוד קיים רק אם הוא
   באמת משרת את המטרה.
3. **תהליך ה-review עצמו.** ככה נראה review של מהנדס טוב:
   1. מבין מה ה-MR מנסה לעשות.
   2. ממפה את ה-blast radius: מי קורא לסימבולים ששונו, גם מעבר לגבולות של package או
      ספרייה.
   3. מנסח השערות.
   4. חוקר כל השערה עד שהיא מאומתת או מופרכת.
   5. מאמת את הממצא באופן עצמאי.
   6. כותב הערה עם שרשרת ראיות.

   תחשוב על sub-agents שעובדים במקביל, על verifier אדברסרי לכל ממצא, ועל דרישה שלכל
   הערה תהיה שרשרת `file:line` מהשינוי ועד הכשל.
4. **exploration שחוצה ספריות.** צריך:
   - find-references ו-callers, לא רק definitions.
   - call graph (tree-sitter, ctags, LSP או SCIP).
   - git log ו-git blame.
   - קריאה של קבצים מלאים.

   אם "ספרייה" היא repo נפרד או package פנימי, צריך לחשוב איך מביאים אותה בגרסה הנכונה.
   ואם אפשר להריץ טסטים, type-checker או linter ב-sandbox כדי לאשש השערה, זו הראיה
   החזקה ביותר שיש.
5. **החצי השני: אימות תיקונים וטענות.** ה-replier וה-verdict צריכים להפוך ל-agents עם
   tools. הם צריכים לקרוא את ה-thread ואת ה-diff מאז ההערה, ללכת לאן שהמפתח מצביע, לבדוק
   שהתיקון מכסה את כל המקרים ולא רק את השורה שסומנה, ולחזור בהם כשהבודק טעה. הם גם צריכים
   לסרב להסכים ל"תוקן" כשבפועל לא תוקן.
6. **זיכרון והבנה של ה-repo.** ידע מתמשך לכל repo: ארכיטקטורה, קונבנציות ופידבק שנלמד.
   הוא נבנה ומתעדכן ברקע, כדי שכל review לא יתחיל מאפס.
7. **observability.** צריך לשמור את המסלול המלא של כל ריצה: tool calls, ה-reasoning,
   ואילו ממצאים נפסלו ולמה. וצריכה להיות דרך להריץ אותו שוב. בלי זה אי אפשר להבין למה
   הבודק פספס.
8. **רעש.** reviewer חזק יותר נוטה לדבר יותר. בוט שמציף MR בהערות חלשות מקבל mute תוך
   שבועיים. חשיבה עמוקה צריכה להוריד את מספר ההערות השגויות, לא להוסיף הערות.

## סקר open source

תסקור agents בקוד פתוח כדי לראות מה אפשר לשלב או ללמוד מהם. לפחות את אלה:

- Hermes Agent (Nous Research)
- OpenHands
- opencode
- Codex CLI
- Qwen Code (רלוונטי במיוחד אם נבחר ב-Qwen)
- Goose
- mini-SWE-agent / SWE-agent
- Aider
- PR-Agent

רק כמקור לרעיונות, לא לשילוב: ה-plugin של code-review ב-Claude Code
ו-`claude-code-security-review` של Anthropic. אלה מעניינים בגלל איך שהם בונים את תהליך
ה-review: כמה reviewers במקביל, שלב אימות ו-confidence.

**תקרא את הקוד ולא רק את ה-README.** תבדוק איך בנויה הלולאה, איך מנהלים context
ו-compaction, איך מעוצבים ה-tools, sub-agents וזיכרון.

לכל אחד תבדוק:

- **סינון ראשון:** רישיון open source, ופריסה offline מלאה. כלומר: כל התלויות ניתנות
  ל-vendoring, ואין טלמטריה או קריאות החוצה שאי אפשר לכבות.
- האם הוא עובד מול LiteLLM, או מול endpoint שתואם ל-OpenAI.
- כמה טוב הוא עובד עם Qwen ועם GLM.
- האם יש מצב headless עם פלט מובנה.
- sandboxing.
- כמה פעילה התחזוקה.

אפשר להשתמש ב-sub-agents כדי לסקור כמה במקביל.

## איך נדע שהגענו

אין צורך לבנות תשתית מדידה כבדה לפני המוצר. מה שכן צריך:

- **תרחישים מציאותיים ל-demo.** ששה עד עשרה תרחישים שמייצגים את מה שחשוב לי:
  - באג שעובר בין 2–3 ספריות.
  - שינוי שנראה נקי ב-diff ושובר משהו רחוק.
  - MR נקי שהבודק צריך לשתוק עליו.
  - מקרים לחצי השני:
    - תיקון אמיתי.
    - תיקון חלקי.
    - "תוקן" בלי שום שינוי.
    - התנגדות מוצדקת.
    - התנגדות לא מוצדקת.
- **קריאה צד לצד.** אם אפשר, תריץ Claude Code על אותם תרחישים (במכונת הפיתוח, לא ב-VPN)
  ותשווה את ה-reviews. זה לא ציון. זו בדיקה פשוטה: האם קורא אנושי היה מעדיף את ההערות
  של הבודק.
- **ה-harness הקיים ב-`eval/`** זמין אם הוא נוח לך. לא חובה.

## איך לעבוד ומה להחזיר

1. **הבנה ואבחון.** תבין איך הגענו לפה (ROADMAP, היסטוריה, קוד), ותאמת או תפריך את מה
   שכתבתי למעלה. אחר כך תכתוב אבחון משלך: איפה בדיוק הבודק מאבד את ההקשר ואת
   ה-reasoning.
2. **סקר ותכנון.** תכתוב מסמך עיצוב ב-`docs/reviewer-v2.md` שכולל:
   - האפשרויות וההשוואה ביניהן.
   - בחירת המודל.
   - ההמלצה שלך וה-trade-offs שלה.
   - הארכיטקטורה: מה נבנה, מה משולב ומה נזרק.
   - איך כל זה מגיע ל-VPN ורץ שם offline.

   **פה עוצרים.** אני רוצה לאשר את הכיוון לפני שבונים.
3. **בנייה.** אחרי האישור: מתחילים מהחלק הכי מסוכן בהימור. תראה אותו עובד על
   התרחישים, ואז ממשיכים למוצר המלא.

`ROADMAP.md` הוא מסמך ההעברה בין sessions. תעדכן אותו לאורך הדרך, כולל ה*למה*, כדי
שה-session הבא יוכל להמשיך מאיפה שעצרת.

ואם משהו כאן לא מתיישב עם מה שאתה רואה בקוד, תגיד.
