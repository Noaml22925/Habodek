# Handoff — getting this running on the VPN machine

You have just moved the repository across as a zip. This file covers the move
itself: what did not come with it, what to install, and how to prove the thing
works before you point it at anything real.

**Read this once, then work from [`DEPLOY.md`](DEPLOY.md)**, which is the actual
deployment checklist. `ROADMAP.md` is the full decision record and explains *why*
anything here is the way it is.

---

## 1. What did not survive the zip

`.gitignore`d files are not in the archive, and two of them are required. Nothing
else here is machine-specific.

| Missing | What it held | What to do |
|---|---|---|
| `agent/.env` | bot token, gateway key, model config | Recreate it — `DEPLOY.md` §3 |
| `local/.env` | local GitLab root password | Only needed for the offline rig |
| `.habodek-work/` | corpus run results and logs | Regenerated by `run_corpus.py` |
| `agent/resource/` | cloned repos, local store data | Recreated at runtime |

If you zipped the working directory rather than `git archive`, you may also be
carrying `.venv/`, `__pycache__/`, `.pytest_cache/` and `agent/bin/`. Delete
them — a virtualenv built on the other machine will not work here.

> **Do not copy `agent/.env` across even if you kept it.** It points at
> `localhost:8929` and `localhost:11434`, holds a token for a throwaway GitLab,
> and every value in it is wrong for production. Start from `agent/.env.example`.

## 2. Check the history came with it

A zip of the working tree has no git history. That matters here, because the fork
delta is the history — `git log 4989776..HEAD` is the complete list of what we
changed on top of upstream, and `agent/NOTICE.md` carries the same list in prose.

```bash
git log --oneline | tail -3      # expect a72f24a, then 4989776, then 1a4254f
git status                       # should be clean
```

`4989776` is upstream vendored untouched, so everything after it is exactly what
we wrote.

If you get "not a git repository", you moved the files without the history. It is
recoverable — the repository is on GitHub as `Noaml22925/Habodek`, so clone that
instead and you lose nothing.

Re-add the upstream remote if it is missing; it is what makes "what did we change"
answerable later:

```bash
git remote add upstream https://github.com/antlss/gitlab-review-agent.git
```

## 3. Prerequisites

| Need | Version used | Notes |
|---|---|---|
| Go | 1.27 (`go.mod` declares 1.25.5) | A newer toolchain building an older module is fine |
| Python | 3.12+ | Only for the evaluation harness, not for the agent |
| C toolchain | mingw-w64 / gcc | **Only if `STORE_DRIVER=sqlite`.** Postgres and file need no CGO |
| Docker | — | **Not needed in production.** Only for the offline GitLab rig in `local/` |

```bash
# Agent
cd agent && go build ./...

# Harness
pip install -e ".[dev]"
```

**On Windows, set line endings before anything else.** `.gitattributes` pins
`eol=lf`, but a global `core.autocrlf=true` overrides it on checkout and the
working tree drifts to CRLF — which makes `gofmt -l` report clean files as
unformatted and turns upstream diffs into noise:

```bash
git config core.autocrlf false       # repo-local, overrides the global setting
git status --porcelain               # MUST be empty; the next line destroys uncommitted work
git ls-files -z | xargs -0 rm -f && git checkout -- .
```

On Linux or macOS this is a non-issue; skip it.

## 4. The VPN machine has no internet

It cannot reach `proxy.golang.org`, `sum.golang.org`, or any module host, so a
plain `go build` dies partway through resolving dependencies. Two symptoms, one
cause:

- `verifying golang.org/x/mod@v0.8.0/go.mod: ... 404` — the checksum database is
  unreachable.
- `unrecognized import path "dario.cat/mergo": ... lookup dario.cat ... server
  misbehaving` — `GOPROXY=direct` asking DNS to resolve a vanity import path.

Do not try to fix either one with `GOPROXY` or `GOSUMDB`. **The Go dependencies
are vendored in `agent/vendor/`** and travel with the zip. Go detects that
directory and builds from it automatically:

```bash
cd agent && go build ./...     # no network, no GOPROXY, no `go env -w`
```

To prove the build is genuinely offline rather than quietly using a warm cache:

```bash
cd agent
GOFLAGS=-mod=vendor GOPROXY=off GOMODCACHE=$(mktemp -d) go build ./...
```

### Refreshing the vendor tree

`vendor/` is committed, so it changes only when dependencies do — and that has
to happen on a machine **with** internet:

```bash
cd agent
go mod vendor                    # rewrites vendor/ and vendor/modules.txt
go build -mod=vendor ./...       # confirm before committing
git add vendor && git commit
```

`.gitattributes` marks `vendor/** -text`, so a global `core.autocrlf` cannot
rewrite third-party sources the way section 3 describes for the rest of the tree.

### Python

Same shape, from the wheelhouse that ships alongside the source:

```bash
pip install --no-index --find-links wheels -e ".[dev]"
```

Those wheels are built for **CPython 3.12 on linux x86_64**. On any other
interpreter or architecture they will not install; re-download them off-VPN
using the command recorded in the transfer bundle's `TRANSFER.md`.

### Docker

`agent/Dockerfile` no longer runs `go mod download`, so its Go build stage is
offline. `docker build` as a whole is not: it still needs a registry for the
`golang:1.25-alpine` and `alpine:latest` base images and an apk mirror for
`git`, `gcc`, and `musl-dev`. If the machine has neither, build the binaries
directly with `go build` — nothing in production requires the container.

## 5. Prove it works before touching the VPN

None of this needs the company GitLab or the gateway, and all of it should pass
on a fresh machine. If something here fails, fix it before going further —
otherwise you will be debugging two problems at once.

```bash
cd agent
go build ./... && go vet ./...
go test ./...
gofmt -l .                 # expect no output

cd ..
python -m pytest tests/ -q # expect 42 passed
ruff check .
```

`go test -race ./...` needs CGO and therefore a C toolchain. Worth running before
you ship anything concurrent; skip it if you have no gcc and are not touching the
worker pool.

## 6. Then: `DEPLOY.md`

That file is the whole of what remains, written to be worked top to bottom:

2. Configuration — the required variables and the ones that bite
3. Webhook registration
4. **The three genuine unknowns**, each with a test: does your gateway accept the

6. Scoring it against the real model — and the sampling-variance trap that makes
   single-run comparisons meaningless

## 7. Two things to know before you start

**The local score is not a prediction.** F5 measured noise 0, precision 100%,
detection 62% against a local 8B model. Repeating that run *without changing
anything* gave noise 1, precision 71%, detection 38%. Those numbers validated
plumbing, not review quality, and they are one draw from a high-variance process.
Do not carry them into a conversation about what the bot will do on real code.

**Nothing runs unless somebody asks.** Reviews trigger on the `ai-review` label
(`REVIEW_TRIGGER_LABEL`). That is the cost control, it is deliberate, and it means
you can deploy the server safely before deciding which repositories to open up.
