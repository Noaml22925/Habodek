# F6 — Deploying Habodek

Everything here needs the VPN, which is why none of it is done. Everything that
*could* be done without it already has been, so this is a checklist, not a
design document. Work top to bottom; each step is verifiable before the next.

`ROADMAP.md` is still the handoff document and the source of truth for *why*.
This file is only *how*, for the one milestone that cannot be rehearsed offline.

---

## 0. What you are carrying over

The whole repository. Nothing is machine-specific except the gitignored files,
which do **not** transfer and must be recreated:

| File | Holds | Recreate with |
|---|---|---|
| `agent/.env` | bot token, gateway key, model config | step 3 below |
| `local/.env` | local GitLab root password | not needed in production |
| `.habodek-work/` | corpus run outputs | regenerated by `run_corpus.py` |

`local/` as a whole is the offline rehearsal rig. It is not part of the
deployment — keep it, it is how you re-test after any prompt change.

## 1. Preflight: what is already proven, so you do not re-debug it

Do not spend VPN time on these. They were verified locally and the findings are
in `ROADMAP.md` under *Gotchas*.

- **Build, vet, full test suite, race detector** — all clean.
- **Webhook signature checking works.** `internal/handler/webhook/handler.go`
  compares `X-Gitlab-Token` against `GITLAB_WEBHOOK_SECRET` with `hmac.Equal`,
  and `ValidateForServer()` refuses to start the server without the secret set.
  There is no "forgot to turn on auth" failure mode available here.
- **The whole loop runs**: webhook → queue → clone → agentic review → threaded
  comment on a diff line → reviewer replies → agent answers from the repository.
- **Rejected findings feed back into the next review.** A developer replying
  "false positive" is classified, stored, and re-injected into the next review's
  prompt as recent developer feedback. This is wired end to end.
- **`max_completion_tokens`** (not `max_tokens`) is what `internal/pkg/llm/openai.go`
  sends. Ollama accepted it. LiteLLM normally normalises it too — see step 5 if
  the real gateway disagrees.

## What is genuinely unknown until you are on the VPN

Only three things, and they are all in step 5:

1. Does the gateway accept the exact request body `openai.go` builds?
2. Does qwen3.6 do tool calling through it?
3. What is qwen3.6's real context window?

## 2. The bot account

The agent posts as whoever owns `GITLAB_TOKEN`. Use a dedicated account, not a
person's — the agent's threads should be attributable to the bot, and a personal
token dies when that person's access changes.

- Create the user, e.g. `habodek-bot`.
- Give it **Developer** on every repository it reviews. Reporter is not enough:
  it needs to create discussions and resolve them.
- Issue a personal access token with the **`api`** scope.
- **Write down its numeric user id.** This is `GITLAB_BOT_USER_ID`, and getting
  it wrong makes the agent reply to its own comments in a loop. It is the single
  most damaging misconfiguration available. `GET /api/v4/user` with the bot's own
  token returns it.

## 3. Configuration

Copy `agent/.env.example` if present, otherwise start from this. Values marked
**required** will refuse to start without them.

```bash
# --- GitLab -----------------------------------------------------------
GITLAB_BASE_URL=https://gitlab.internal.example        # required
GITLAB_TOKEN=<bot personal access token, api scope>    # required
GITLAB_WEBHOOK_SECRET=<long random string>             # required for the server
GITLAB_BOT_USER_ID=<the number from step 2>            # required; loop guard

# --- Gateway ----------------------------------------------------------
LLM_DEFAULT_PROVIDER=openai                # LiteLLM speaks the OpenAI protocol
LLM_DEFAULT_MODEL=<the gateway's name for qwen3.6>
OPENAI_BASE_URL=https://litellm.internal.example/v1    # note the /v1
OPENAI_API_KEY=<gateway key>
LLM_CONTEXT_WINDOWS=<model>=<real window>  # see step 5, do not guess
# LLM_SEED=1234                            # measurement runs only; see step 7

# --- Storage ----------------------------------------------------------
STORE_DRIVER=postgres                      # see the note below
DATABASE_URL=postgres://...                # required when driver is postgres

# --- Cost control -----------------------------------------------------
REVIEW_TRIGGER_LABEL=ai-review             # nothing runs without this label
REVIEW_MAX_FINDINGS=10
WORKER_POOL_SIZE=5
```

**On `STORE_DRIVER`:** local runs use `file`, which is fine for one machine and
wrong for a service — it does not survive concurrent processes or a container
restart onto fresh storage. Use `postgres` in production. `sqlite` works and
needs CGO at build time; postgres does not, which makes the container simpler.

**Generate the webhook secret properly** — it is the only thing standing between
your agent and anyone who can reach its port:

```bash
openssl rand -hex 32
```

## 4. Webhook registration

Per project, or at group level if you want it everywhere at once:

- URL: `https://<where the agent runs>/webhook/gitlab`
- Secret token: the same `GITLAB_WEBHOOK_SECRET`
- Trigger: **Merge request events** only. Nothing else is consumed, and the
  fewer events arrive the less there is to rate-limit.

The agent must be reachable from the GitLab server, which in a real network is
usually the step that takes longest. Test with GitLab's own "Test" button before
blaming the agent.

> The local rig needed `host.docker.internal` here. That is a Docker-on-Windows
> artefact and has nothing to do with production — use the real hostname.

## 5. The three unknowns, in the order to test them

### 5a. Does the gateway accept our request body?

Before starting the server, prove the transport. This is the same check that
settled the question against Ollama:

```bash
curl -sS "$OPENAI_BASE_URL/chat/completions" \
  -H "Authorization: Bearer $OPENAI_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "<LLM_DEFAULT_MODEL>",
    "messages": [{"role": "user", "content": "Read the file src/main.go"}],
    "max_completion_tokens": 256,
    "tools": [{"type": "function", "function": {
      "name": "read_file",
      "description": "Read a file from the repository",
      "parameters": {"type": "object",
        "properties": {"path": {"type": "string"}},
        "required": ["path"]}}}]
  }'
```

You are looking for two things: **HTTP 200**, and a response whose
`finish_reason` is `tool_calls` with a well-formed `read_file` call.

- A 400 mentioning `max_completion_tokens` is the one known incompatibility.
  The fix is one word in `internal/pkg/llm/openai.go` — change it to
  `max_tokens`. Record it in `agent/NOTICE.md` if you do.
- A 200 with ordinary prose and no tool call means tool calling is not working
  through the gateway. **Stop and fix that before anything else** — the whole
  value of this fork over PR-Agent is agentic repo exploration, and without tool
  calls it degrades to a diff-only reviewer.

### 5b. What is qwen3.6's real context window?

Ask the gateway rather than guessing — `GET $OPENAI_BASE_URL/model/info` on
LiteLLM lists `max_input_tokens` per model. Then set it:

```bash
LLM_CONTEXT_WINDOWS=<exact model name>=<that number>
```

**Do not skip this.** Any model absent from the built-in map is assumed to be
128k. If the real window is smaller, the gateway truncates and the agent reviews
a partial file **without any error**, which degrades reviews silently — the worst
way for this to fail. The model name must match `LLM_DEFAULT_MODEL` exactly.

### 5c. Does a real review work?

One MR, no webhooks, nothing posted until you are happy:

```bash
cd agent && go run ./cmd/cli review --project-id <id> --mr-id <iid>
```

This needs a live GitLab even for a dry run — it fetches the project and MR
first. Read the output before enabling the webhook on anything.

## 6. Turning it on

```bash
cd agent && go run ./cmd/server     # or the container; listens on :8080
```

Then label one merge request `ai-review`. Nothing happens without the label —
that is the cost control, and it is deliberate.

Two behaviours that look like bugs and are not:

- **Re-labelling does not re-trigger.** Deduplication is on project + MR + head
  SHA within 30 minutes. To force a re-review, push a commit.
- **A push re-triggers on its own** via the MR update event, and the second pass
  over fixed code correctly posts nothing.

## 7. Score it against the real model — this is the point

The local score (noise 0, precision 100%, detection 62%) measured an 8B model.
It validated the plumbing and says nothing reliable about review quality. The
run that matters is this one:

```bash
python local/run_corpus.py --out .habodek-work/results-prod.json --keep-logs
python -m habodek.cli eval --from-json .habodek-work/results-prod.json --verbose
```

`run_corpus.py` needs the 13 corpus cases seeded as MRs somewhere it can reach.
Point it at whatever GitLab you are using with `--base-url` and `--token`; seed
them with `local/seed_gitlab.py` if they are not already there. It never posts
and never labels, so it cannot disturb real repositories — but seed it into a
scratch group anyway, not alongside production projects.

**Set `LLM_SEED` before the first measured run, and run each configuration at
least three times.** This is not optional caution, it is the finding of F5.1:
locally, two runs of an *identical* configuration differed by three detections
and by one false positive on a clean case — more than any prompt change made so
far. Without a pinned seed, an A/B on the gateway will read its own sampling
noise and charge you for the privilege. The seed is omitted from the request
when unset, so it changes nothing until you set it.

**Read the numbers in this order**, and the order is the whole opinion of the
harness:

1. **Noise on clean cases.** Must stay at 0. This is what decides whether the
   team keeps the bot switched on. Everything else is negotiable against it.
2. **Precision.**
3. **Anchored on the flaw.** Not a quality metric — it says how often a correct
   finding was attached to the wrong line.
4. **Detection.** Last on purpose. A reviewer that flags everything scores 100%.

### Now, and only now, tune

The prompts were deliberately left alone locally because tuning against an 8B
model measures the wrong thing. Against the real model, these are the levers, in
the order worth pulling:

- **Detection is low and noise is still 0** → relax
  `Prefer false negatives over false positives` in
  `StructuredExtractionSystemPrompt` (`internal/core/prompt/structured_review_prompts.go`).
  This is the real trade: detection bought with noise. Re-run and check metric 1
  did not move.
- **One finding per review, on cases with two flaws** → that was an 8B artefact,
  not a cap; `REVIEW_MAX_FINDINGS` is 10 and never bound. If it persists on
  qwen3.6 it is a genuine prompt problem worth attacking.
- **`typos` scores two permanent misses** → that is policy, not failure. The
  extraction prompt bans documentation and naming findings. Decide it here:
  either widen the allowed categories (a typo in a user-facing string arguably
  *is* production impact) or move the case out of `expect`. Do not leave it
  ambiguous — it drags detection down for a reason unrelated to reviewer skill.

Re-run the two commands after every change. That loop is the entire reason the
eval harness exists.

## 8. Pilot (F7)

One friendly repository, one team that will tell you when it is wrong. Watch
noise, not detection — a bot that is occasionally silent is tolerated, a bot that
is often wrong gets muted within a week and never gets a second chance.

The self-learning loop is already wired: a developer replying "false positive"
is classified, stored, counted, and injected into later reviews as recent
feedback. Prompt consolidation runs on a cron (`CRON_FEEDBACK_CONSOLIDATE_SCHEDULE`,
Mondays at 02:00) once a project has accumulated enough feedback. So the pilot
improves the reviewer as a side effect of being used — which means it is worth
telling the pilot team that replying to the bot is useful, not wasted breath.
